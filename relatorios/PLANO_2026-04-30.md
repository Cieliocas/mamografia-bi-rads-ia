# Plano de Implementação — AIdentify
**Data:** 2026-04-30
**Contexto:** App desktop local para radiologista. Modelo de IA será treinado depois;
até lá, a ferramenta deve ser totalmente utilizável apenas para visualização e anotação.

---

## Plano A — Sem modelo (uso imediato pelo radiologista)

Objetivo: entregar uma `.app` instalável que o radiologista usa no PC dele, sem
depender do sidecar Python ou de qualquer modelo.

### A.1 — Degradação suave da IA (🔴 prioridade alta)
**Porquê:** evitar que a ausência do sidecar quebre o fluxo principal.
- [ ] Auditar todos os pontos onde o frontend chama `/api/tasks/predict` ou
  depende de `backendOnline === true` para funcionalidades não-IA
  (abrir, visualizar, anotar, exportar)
- [ ] Status bar: distinguir "Go Core offline" (bloqueante) de
  "AI offline" (apenas desabilita o botão "Analisar")
- [ ] Botão "Analisar com IA" → desabilitado + tooltip "IA não disponível"
  quando `/readyz` reporta sidecar offline
- [ ] Go core: `/healthz` deve retornar 200 mesmo sem sidecar; `/readyz`
  reporta `ai_engine: "unavailable"` em vez de erro
- [ ] Guardian: não tentar restartar o sidecar se `.venv` não existir
  (variável `AI_ENGINE_DISABLE=1` ou auto-deteção)

### A.2 — Build de distribuição (🔴 prioridade alta)
**Porquê:** sem um `.app` instalável, não há entrega real.
- [ ] `wails build -platform darwin/universal` produzir `AIdentify.app`
- [ ] Embed do Go core no binário Wails (já está via `//go:embed all:dist`)
- [ ] Decidir bundling do sidecar Python:
  - **Opção 1:** não bundle — radiologista não usa IA; `.app` puro
  - **Opção 2:** bundle do `.venv` dentro do `Resources/` para futuro uso
  - **Recomendação:** Opção 1 para já; trocar para Opção 2 quando houver modelo
- [ ] Code-signing ad-hoc para macOS (sem developer ID): `codesign --force --deep --sign -`
- [ ] Documentar instalação: arrastar `.app` para `/Applications`,
  primeira execução com clique direito → "Abrir" (Gatekeeper)
- [ ] `Mammo-Desktop-Dev.command` continua a funcionar para dev local

### A.3 — Polish do fluxo do radiologista (🟡 média)
**Porquê:** uso real revela atritos que não aparecem em demos.
- [ ] WW/WC: usar `meta.WindowCenter/WindowWidth` do header DICOM como default
  ao abrir um estudo (já lemos do header no Plano 04 reader)
- [ ] Atalhos de teclado:
  - `Espaço` = pan, `+/-` = zoom, `R` = reset
  - `1..5` = BI-RADS rápido na anotação selecionada
  - `Cmd+Z` / `Cmd+Shift+Z` = undo/redo
- [ ] Undo/redo de anotações (stack no `ViewerStateService`)
- [ ] Auto-save: persistir anotações ao Go core a cada N segundos ou ao perder foco
- [ ] Toast notifications consistentes (já há modal; falta toast para sucesso/erro
  de export e save)
- [ ] Lista de estudos recentes na splash/home

### A.4 — Robustez DICOM (🟡 média)
**Porquê:** o reader atual rejeita compressão; mamografias clínicas raramente vêm
descomprimidas.
- [ ] Suporte a JPEG-Lossless / JPEG-LS (transfer syntaxes mais comuns em MG):
  - Avaliar `gocv` + libjpeg ou shell-out para `dcmtk` (`dcmdjpeg`)
  - Ou: usar `pydicom` no sidecar como fallback de descompressão
- [ ] Multi-frame: ler todas as frames (não só `Frames[0]`), permitir navegação
- [ ] LUT/VOI sequence: aplicar `VOILUTSequence` se presente em vez do WW/WC linear
- [ ] Pixel signedness: respeitar `PixelRepresentation` para escolher int16 vs uint16

### A.5 — Persistência e backup (🟢 baixa, mas crítica para uso clínico)
**Porquê:** SQLite local é o ponto único de falha.
- [ ] Botão "Backup base de dados" → exporta `.db` para diretório escolhido
- [ ] Importar `.db` existente (com confirmação)
- [ ] Versão automática do schema com migrations idempotentes
- [ ] Mensagem clara se a DB ficar corrompida + recovery via último backup

### A.6 — Documentação radiologista (🟢 baixa)
- [ ] README "como instalar" + screenshots
- [ ] Guia de 1 página: abrir DICOM → anotar → exportar relatório
- [ ] Disclaimer claro: "Versão sem assistente de IA. Funcionalidade de IA será
  ativada em release futuro."

## Plano B — Com modelo (quando o treino estiver pronto)

Objetivo: ativar o pipeline AI e entregar findings sugeridos ao radiologista,
mantendo-o no controle (a IA propõe, o radiologista decide).

### B.1 — Integração ONNX no sidecar (🔴 prioridade alta)
- [ ] `onnxruntime` ou `onnxruntime-gpu` em [apps/ai-engine/requirements.txt](apps/ai-engine/requirements.txt)
- [ ] Loader de modelo: caminho via `MODEL_PATH` env var, validar `model.onnx`
  na inicialização, falhar `/readyz` se ausente ou inválido
- [ ] Substituir mock em `app/main.py POST /predict` pela inferência real
- [ ] Pré-processamento: depende do modelo (resize, normalização, ROI crop) —
  documentar em `apps/ai-engine/PREPROCESS.md`
- [ ] Pós-processamento: NMS, threshold de confiança, mapeamento para
  `RichFinding{BIRADS, BBox, confidence}`
- [ ] Multi-modelo: suportar troca via `POST /reload?path=...` para A/B testing

### B.2 — Bundling do Python no `.app` (🔴 alta)
- [ ] Mudar para Opção 2 do A.2: incluir `.venv` no `Resources/`
- [ ] Resolver paths: `resolvePython()` no Guardian já procura `.venv/bin/python`,
  ajustar para `Resources/python/bin/python` no `.app`
- [ ] Modelo `.onnx` em `Resources/models/` ou descarregado on-demand do servidor
  ICIT (com cache local)
- [ ] Tamanho do `.app`: medir antes/depois; modelo + ORT podem somar 200-500 MB

### B.3 — UX da assistência IA (🟡 média)
- [ ] Toggle "Mostrar sugestões de IA" no viewer
- [ ] Findings sugeridos com badge "IA" e cor distinta dos manuais
- [ ] Aceitar / rejeitar sugestão individualmente → converte em anotação manual
  ou marca como `dismissed`
- [ ] Confidence visível (% ou barra)
- [ ] Filtro: BI-RADS mínimo, confidence mínimo
- [ ] Telemetria local opt-in: agreement rate (radiologist vs IA) para ajudar
  a melhorar treino futuro

### B.4 — Treino e ciclo de melhoria (🟡 média)
**Porquê:** as anotações do radiologista são dados de treino para o próximo modelo.
- [ ] Export do dataset (`/api/export?format=json|csv`) já existe;
  adicionar campo "annotations" com BI-RADS, BBox, autor, timestamp
- [ ] Anonimização: stripping de PHI no export (PatientID, nomes) — opcional
- [ ] Pipeline de treino documentado em [projetos/treinamento/](projetos/treinamento/)
- [ ] Versão do modelo: `meta.json` com `version`, `trained_on`, `metrics`
  fica ao lado do `.onnx`; UI mostra qual versão está ativa

### B.5 — Validação clínica (🔴 antes de release com IA)
- [ ] Ground-truth set local com casos validados pelo radiologista
- [ ] Métricas: sensibilidade, especificidade, AUC por categoria BI-RADS
- [ ] Disclaimer atualizado: "Ferramenta de auxílio. Decisão final é do médico."
- [ ] Logs de inferência (anonimizados) para auditoria

### B.6 — CI/CD (🟢 quando houver releases públicos)
- [ ] GitHub Actions: `go test`, `pytest`, `ng test`, `wails build`
- [ ] Release pipeline: tag → build `.app` → notarização Apple (developer ID)
- [ ] Cache de model artifacts entre builds

## Ordem sugerida de execução

**Sprint 1 (sem modelo, ~1-2 semanas):** A.1 → A.2 → A.3 (core do polish)
→ entregar `.app` v0.1 ao radiologista.

**Sprint 2 (sem modelo, conforme feedback):** A.4 (DICOM compressão se aparecer
nos casos reais) → A.5 (backup) → A.6 (docs).

**Sprint 3+ (após treino):** B.1 → B.2 → B.3 → B.5 → release v1.0 com IA.

**Adiar:** B.6 (CI/CD) até haver pipeline de releases regular.
